# 一起看类项目横向调研（2026-10-01）

目的：回答"雨见怎么做/声音怎么解决"，并对照 5 个开源实现，为声音档方案（默认档+麦开关）
与 B 方案的长期定位提供参照。

## 一、雨见浏览器（本地逆向记录 yjllq-together-watch.md / -float-window.md）

- **双方打开同一个网站** ✓：注入 JS 挑页面 `<video>`（querySelectorAll('video') ×14），
  直接读写 `currentTime =` / `.paused` —— 两边各自在页面里播，只同步进度。
- **声音 = 各自本地播的视频原生音轨**，不传声音。
- **无语音通话功能**：全部 dex 无语音/麦克风/RTC 通话相关命中（用户判断与证据一致）。
- 房间号 + Redis 中转（自有服务器）。

## 二、五个开源项目

| 项目 | 一起看方式 | 声音 | 同步机制 |
|---|---|---|---|
| **Piik**（TNTcraftHIM）| **屏幕共享**流派（不是同步播放器）：分享屏幕/窗口/标签页，朋友浏览器看 | 分享源的画面+声音（桌面浏览器 getDisplayMedia 可捕获标签页音频）+ **麦克风解说（可选）** | P2P 优先 + 可自托管 SFU 转发；房间制，1 主 + 20 观众 |
| **star-syncplayer**（星星同步播放器）| 桌面端（JavaFX+VLC）**双方各自打开同一个视频文件** | 各自本地 VLC 原声；弹幕；**无语音** | SpringBoot WebSocket：服务器同时向两边发指令，延迟差 = \|t1−t2\| |
| **SyncPlayer**（ConstStar）| README 不可得，仅目录可见 Client/Server + web 客户端（2021，异地情侣一起看电影）| 未知 | 未知（C/S 结构）|
| **SyncWatch**（xuange6610）| **媒体由房主自托管服务器经 HTTP Range 分发**，各自下载片段本地播（不打开外部网站）；另有"网页同步"=传输画面 | ① 原生音轨随媒体本地播（不走通话）② **WebRTC 语音通话（独立功能）** ③ 屏享时**系统音频优先 WebRTC（内录）**、JPEG/PCM 兜底 | Socket.IO 房间权威状态 + 时间戳/版本广播 + 偏差超阈值才纠偏；心跳/网络防抖 |
| **192_lab-couple-cinema**（情侣影视）| 两人打开**同一个放映厅网页**（自己部署）；片源 = 影库 m3u8（hls.js 各自播）/服务器上传文件/直链 | 各自本地原生音 + **WebRTC 点对点语音通话（独立）** + 弹幕 | Socket.IO 意图转发 + 领队每 4s 广播进度、偏差 >1.8s 纠偏；6 位房间号限 2 人 |

## 三、行业共性（关键洞察）

1. **主流是"各播一份 + 只同步时间轴"** —— 雨见、星星、SyncWatch 的媒体模式、情侣影视、
   我们的 S 档全属此派。**声音天生各自本地，根本不用传** —— 所以这一派没有回声/麦的问题。
2. **只有"传画面"流派**（Piik、SyncWatch 屏享模式、我们的屏幕分享/B 方案）才要解决声音：
   - 桌面浏览器能**内录**（getDisplayMedia audio）→ Piik/SyncWatch 不用麦收外放；
   - **移动端才卡在"系统只有话筒插孔"** —— 我们项目 VoiceMode.kt 注释里 javap 核实过的限制。
3. **语音通话与视频声是两条独立通道**（SyncWatch、情侣影视都有语音，但语音从不背视频声的锅）。
4. 对我们的定位印证：
   - S 档（各播一份+对时）= 主流做法，无声音传输问题；
   - 复杂度来自我们叠加了屏幕分享 + B 方案 + 语音三件事；
   - 声音档"默认档+麦开关"是低成本改进；**内录直传**只在移动端为真痛点（耳机观影/静音外放）时才值得动底层 —— 桌面方案先例（SyncWatch）证明该路对，但成本在移动端 SDK 层。
