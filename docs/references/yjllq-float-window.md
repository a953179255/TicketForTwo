## 2. 机制拆解

### 2.1 证据（前作 APK 字符串留存）

| 命中 | 含义 |
|---|---|
| `悬浮失败` / `悬浮播放失败2` / `悬浮播放失败4` | 确实有一条"悬浮播放"路径，且失败**分了两种码** —— 说明"起窗"与"起播"是两步，各自会失败 |
| `querySelectorAll('video')` ×14、`.currentTime =` ×4、`.paused` ×8 | 页面内播放器用注入 JS 读写（这是"一起看"的对时路径，**不是**浮窗） |
| `打开视频失败`、`房间号`、`重启` | 房间号制；有"打开视频"这一步 = 存在独立起播动作 |

### 2.2 推理（由平台机制与用户观察倒推，非直接证据）

**决定性的一条：换页后浮窗仍在播。**

网页里的 `<video>` 是 DOM 节点 —— 页面一卸载（导航到别的网址），这个节点连同它的播放状态
一起消失。所以**浮窗里播的绝不可能是页面里那个元素**，只能是：

1. **嗅探拿到直链**：WebView `shouldInterceptRequest` 看资源请求，认出 m3u8/mp4/dash →
   我们项目里 `MediaSniffer` 干的正是这件事（Kind.Master / Progressive / Audio）。
2. **另起一个播放器播这条直链**：播放器拿的是 URL，与页面无关 —— 页面怎么跳都不影响它。
   换页时旧页面卸载、页面里那个视频自然停，正好避免两个声音。
3. **要盖在别的 App 上面**：必须是系统级悬浮窗 = `WindowManager` + `TYPE_APPLICATION_OVERLAY`
   + `SYSTEM_ALERT_WINDOW` 权限（这也是为什么它的 Manifest 必然申请这个权限）。
4. **"新视频顶替"**：播放器是**单例** —— 新命中替换播放源，而不是开第二个窗
   （两个窗会互相抢焦点、抢音频，没人那么做）。顶替时大概率还带一次"是否切换"的确认或提示。
5. **回桌面还活着**：靠前台服务保活（进程不被回收），窗口挂 `TYPE_APPLICATION_OVERLAY` 所以
   不属于任何 Activity —— Activity 栈怎么变都不影响它。

> 一句话：**嗅探拿地址 → 独立播放器播地址 → 系统级浮窗承载 → 单例顶替 + 前台服务保活。**

### 2.3 我们能借鉴什么 / 不能借鉴什么

- 能借鉴：上面那条四段式，以及"单例顶替"的规则（避免多窗打架）。
- 不能照搬：他们的形态是**每台设备各播一份 + 服务器对时**（房间号 + Redis 中转）；
  我们是**一台播、另一台跟进度**（没有服务器）。浮窗对他们是刚需（各播一份才需要自己的窗），
  对我们是"房主自己看"的增强 —— 观众端本来就各自在播，**不受房主开不开浮窗影响**。

## 3. 落到我们项目：家底盘点（2026-09-30 实测 grep）

| 需要的东西 | 状态 | 位置/说明 |
|---|---|---|
| ① 嗅探拿直链 | ✅ **已有** | `cinema/MediaSniffer.kt`（认 Master/Progressive/Audio，按面积挑主视频） |
| ② 独立播放器 | ❌ **缺** | 全仓无 exoplayer / media3 / ijkplayer 依赖 → 需加 `media3-exoplayer` + `media3-exoplayer-hls` |
| ③ 悬浮窗权限 | ⚠️ **声明了但没引导** | `AndroidManifest.xml:20` 有 `SYSTEM_ALERT_WINDOW`；代码里**没有任何** `canDrawOverlays` / `ACTION_MANAGE_OVERLAY_PERMISSION` 引导 |
| ④ 切后台保活 | ✅ **已有** | `ShareService.kt`（`startForeground`，Android 14+ 类型化前台服务已处理） |
| ⑤ 浮窗承载 | ❌ **缺** | 无 `WindowManager.addView` 相关代码 |

**结论：五件里有两件现成（嗅探、保活），一件只差引导（权限），要新写的是播放器接入 + 浮窗 UI。**

## 4. 两个必须处理的冲突（我们特有，雨见没有）

### A. 两套播放源 → 时间轴只能有一个

浮窗一开，就存在"页面里的视频"和"浮窗里的播放器"**两个进度**。观众跟的是房主广播的时间轴
（`CallSession.publishCinemaProgress`），两个源同时跑必然打架（正是 2026-09-29 修过的
"进度循环"那类问题的放大版）。

规则（建议）：
- 浮窗起来 → **页面里的视频暂停**，浮窗播放器成为**唯一进度源**并接管广播；
- 关掉浮窗 → 把浮窗进度 `seek` 回页面里的视频，再恢复播放，广播源切回去。

### B. 正在"分享我的屏幕"时，浮窗会被采集进去

`TYPE_APPLICATION_OVERLAY` 的窗口在屏幕上，MediaProjection 采集时可能把它一起录进去
（或者像前作 §24 记的那样出现黑框/重影，取决于承载它的 Surface 类型）。

规则（建议）：**正在分享屏幕时，浮窗自动隐藏**（或降级为不可见），停止分享再恢复。
放映厅（观众各播一份）模式下不采集屏幕，浮窗可自由显示。

## 5. 代价与风险（给非技术视角）

- 安装包大约 **+2MB**（ExoPlayer + HLS）。
- **悬浮窗是敏感权限**：要跳到系统设置里手动开；魅族 Flyme 有悬浮窗管理，默认可能关；
  部分用户看到会犹豫 → 需要一段说人话的解释文案。
- 多一个播放器实例 = 多一点内存占用（约 30–60MB 高峰期）。
- 工作量估计 **1.5–2 天**（播放器接入 + 浮窗服务 + 权限引导 + 顶替规则 + 与进度广播联动）。
- 合规：Google Play 对 `SYSTEM_ALERT_WINDOW` 审核严格 —— 目前自分发，暂不受影响。

## 6. 建议的落地顺序（先小后大）

1. **第 1 档 · App 内浮窗**（约半天，**不需要敏感权限**）：Activity 内浮层，跨页不停，
   回到首页还在；切到别的 App 就看不见。风险最低，能验证"顶替规则"和"进度源切换"是否顺手。
2. **第 2 档 · 系统悬浮窗**（约 1 天）：加播放器 + `TYPE_APPLICATION_OVERLAY` + 权限引导，
   桌面/别的 App 上也能看。放在第 1 档验证过之后再做。

## 7. 已拍板（2026-09-30 用户确认）与落地顺序

**已定：**
1. **直接上第 2 档**（系统悬浮窗，跨 App），不做第 1 档过渡。
2. **"新视频顶替"要询问** —— 弹一句"换到这个视频？"（继续播旧的 / 换它），不静默顶替。
3. **正在分享屏幕时浮窗自动隐藏**（隐藏视图、播放与进度继续，不是暂停）。
4. §4 的两个冲突按下面这套解法执行。

**§4-A 的解法：单一指挥官 + 先立新后废旧**
- 状态机里只有一个"当前进度源"（网页播放器 / 浮窗播放器），广播只读指挥官的读数；
  另一个必须暂停且静音 —— 不是让两者协商，是根本不让它们同时说了算。
- 开浮窗的交接（四步，顺序不可换）：
  ① 记网页播放器当前位置 T → ② 浮窗按嗅到的 URL 起播（此时网页照播，画面不断）
  → ③ 浮窗 seek 到 T 并**确认真的在播**（有读数、无错） → ④ 才暂停网页播放器、交权。
  反过来（先停后起）会出现一两秒"两个都没播"的空白，观众端会收到假的暂停信号。
- 关浮窗反向走一遍（记位置 → 网页 seek 并起播 → 确认 → 才关浮窗），同样无缝。
- **兜底**：嗅探时顺手记下请求头（referer/cookie/UA），浮窗带同样的头去取；
  仍失败（防盗链类站点）则放弃浮窗、网页照播，提示"这个站的视频没法在浮窗里播"。

**§4-B 的解法**：分享屏幕时只隐藏浮窗**视图**，播放与进度继续（否则观众端会以为暂停了）。

**落地顺序：**
1. 加 `media3-exoplayer` + `media3-exoplayer-hls`（+约 2MB）
2. MediaSniffer 顺带记录请求头
3. 浮窗服务：`WindowManager` + `TYPE_APPLICATION_OVERLAY` + 权限引导（跳转系统设置，
   并给"只在 App 内"的退路）
4. **进度源切换（本篇核心，即上面的交接四步）**
5. 顶替询问弹窗
6. 分享屏幕时自动隐藏视图
7. 与已定的「A 的开关 + 同页迷你窗」合并落地

## 9. 追加需求：嗅探候选要全列 + 标时长（2026-09-30 用户提）

一个网页常有三四个视频（正片 / 预告 / 片头广告）。现状是 `CinemaProbe.bestOf(hits)`
自动挑一个（按面积/时长排序），挑错了用户无法换 —— 用户要求**像雨见一样全列出来并标时长**，
自己分辨哪个是电影、哪个是广告。

### 列表设计（已进效果图）
- 每条：时长（大号、主信息）+ 类型（HLS/MP4/DASH/音频）+ 域名 + 疑似标签（正片/预告/广告）
- 排序：**正在网页里播的置顶**，其余按时长降序（正片通常最长）
- 界面里直接写分辨口诀："最长的多半是正片，十几秒的基本是广告"
- 每条一个「播它」操作；浮窗上给「换片」入口打开同一个列表，选中即走 §7 的交接四步
- 时长拿不到就显示"未知"，**不填假数字**

### 时长怎么拿（按 Kind 分）
| 类型 | 做法 | 可行性 |
|---|---|---|
| HLS (Master) | 拉 m3u8（几 KB 文本）→ 取 media playlist 累加 `EXTINF` | ✅ 稳 |
| Progressive (MP4) | `MediaMetadataRetriever.setDataSource(url, headers)` 读元数据 | ✅ 通常能 |
| DASH (MPD) | 多数 MPD 自带 `mediaPresentationDuration` | ✅ 多数能 |
| 带防盗链 / 取不到 | — | ❌ 标"未知" |

- 请求必须带上嗅探时记下的**同源请求头**（referer/cookie/UA），否则大概率取不到。
- **异步填值**：先出条目、时长后填，避免列表卡顿；用 `StateFlow` 逐条更新，别整表重组。
- 排序要在时长回填后**重排一次**（首屏顺序可能变，用动画过渡，不要突然跳）。

### 落地顺序（接 §7 之后）
8. 候选列表 UI（条目 + 时长异步回填 + 排序 + 「播它」）
9. 浮窗「换片」入口复用同一个列表
10. 与「A 的开关 + 同页迷你窗」合并落地

## 10. 「浮窗出现慢、加载画面更慢」排查记录（2026-09-30，提交 e7a049c）

用户反馈：放映中最小化，浮窗很久才出现，出现后画面还要再等。

### 打点方法（以后直接复用）
`FloatPlayerService.mark(tag)` 以 `FloatPlayer.startMs`（请求启动那一瞬）为 +0ms，
打服务各段耗时；再挂 `AnalyticsListener` 打 LOAD 开始/完成（dataType、耗时、字节、uri）、
清单就位、首帧、READY、挑档结果。日志 tag = `FloatPlay`。

### 实测原始分解（t2test / mux 测试流 / 网速 ~1.5MB/s）
```
+493ms   窗口挂上        ← 其实很快
+725ms   清单就位         ← 124ms，快
+4935ms  首段下载完成      ← 4219ms 下 6.5MB ❌ 网速瓶颈
+10166ms 首帧
```
两个真问题：
1. **窗口 0.5 秒就挂上了，但深底压深壁纸几乎看不见** —— 感知成"窗很慢才出"。
2. **慢的真身是下载**：播放器选了 1080p 档（分片 6.5~13.5MB），1.5MB/s 下一个分片 4~8 秒。

### 修复三件套
- **占位提示**："正在接入画面…" 即刻显示，首帧淡出；播放失败改显原因。
- **缓冲门槛 2500/5000 → 500/500**（media3 1.8 合并成 `setBufferDurationsMs`，
  旧的 `setBufferForPlaybackMs` 已删除）。
- **服务端自挑低档变体**（关键）：后台拉 master 清单，按窗宽预算挑档
  （≤960 宽里带宽最高 → 本例选中 848x480/0.84Mbps，分片 <1MB），失败回落原地址；
  host 把**全部候选**一起传（页面嗅探常给变体清单，从它看不出档位）。

### 关键坑：media3 的 maxVideoSize 对 HLS 初始变体选择无效
约束 1280x720 明确进了选择器（`trackSelector.parameters.maxVideoWidth` 打印可见），
但仍选中 url_8=1080p。**结论：约束不可信，必须自己挑档**（url 前缀即可判断选了哪档：
url_8=fhd / url_6=hq(480p) / url_0=hd）。

### media3 1.8 API 挪位记录
- `MediaLoadData` → `androidx.media3.exoplayer.source.MediaLoadData`，字段是 `dataType` 不是 `loadType`
- `AnalyticsListener.onLoadCompleted(EventTime, LoadEventInfo, MediaLoadData)`（耗时在 LoadEventInfo）
- `DefaultLoadControl.Builder.setBufferForPlaybackMs` 已删 → `setBufferDurationsMs(min,max,forPlayback,afterRebuffer)`

### 结果
挑档成功 → 首帧 **+3048ms**（原 10.2s，快 3.4 倍）；窗口含占位即出。
