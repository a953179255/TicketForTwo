# 放映厅方案（v2.1）—— 厅先开，人先进来，片子后选

- 日期：2026-09-25　状态：**方向已定（S 档先行、播放器只做"够放片"、A 档缓做），剩三条新问题待拍**
- 效果图：`docs/mockup/cinema-room.html`（第 3 节是厅的四个时刻；第 4 节那颗「只看画面」开关可以点开对比）
- 取代：`docs/DESIGN-framing.md`（房主侧逐帧裁剪）—— 用户否掉了，理由成立，见 §1
- **v2 → v2.1 的唯一改动来自用户一句话**："必须需要有视频播放才能开始打开放映厅吗？
  我想先打开放映厅，对方先进来，然后我再选择播放什么视频。"
  这条改的不是按钮位置，是**主体**：厅才是入口，放映是厅里的一个动作 ⇒ 见 §3。
- 起因（用户前三段话里的四条诉求）：
  1. "观看端感觉有点割裂" —— 不该看到别人的手机桌面
  2. "分享端屏幕上的 UI 控件和观看端上面的 UI 重叠了" —— 一层 UI 原则被破坏
  3. "我打开浏览器的播放器了，然后我还要去打开双人票这个软件" —— 流程要切 App
  4. "是不是根据一个开源的浏览器进行改造，或者自己重新开发一个浏览器" —— 用户在自己想方案，需要成本判断

## 1. 先认错：取景为什么不该做

用户给的两条理由，第二条我上一版完全没考虑到：

1. **"手机画面也就那么一点，取景之后对方全屏观看肯定模糊"** —— 这句是对的，但归因要修正一下：
   **糊不糊跟裁不裁没关系**。只要画面是从房主屏幕截下来的，它的分辨率上限就是"房主屏幕上那块播放器的物理尺寸"。
   裁一刀不会让它更糊，也不会让它更清 —— 只是把同一批像素重新分配码率。真正的天花板在这儿：

   | 路径 | 观众拿到的有效水平像素 | 在他 2400 宽的横屏上放大倍数 |
   | --- | --- | --- |
   | 整屏分享（现状：采集比例 0.75） | 810 | **3.0×** |
   | 房主侧取景（就算采集拉满 1.0） | 1080 | **2.2×** |
   | 观众本地播 1080P 片源（S 档） | 1080（源就是 1080） | **1.0×** |

   所以取景最多把 3.0× 改善到 2.2×，**天花板是"屏幕"这个物理事实**，改不了。
   要 R2（全屏清晰）只有不传画面这一条路。

2. **"取景总会框多框少，画面不完整或多一块，强迫症难受"** —— 这条更致命，因为它把风险摊给了**最不该负责的人**：
   框是房主侧的，框错了观众难受、房主还得重框，而且中途改框会触发编码器重启（一帧停顿）。
   自动检测在夜景片/纯黑开场这类内容上必然有失手率，我上一版把它当兜底，其实它当不了主路径。

**结论**：取景这条技术路线作废。但它想解决的"一层 UI"这个目标是对的 —— v2 用"根本不传屏幕"来达成，
而不是"把屏幕裁干净"。

## 2. 需求梳理（五条，每条都要能用数字验收）

| 编号 | 需求 | v1 取景 | v2 放映厅 |
| --- | --- | --- | --- |
| **R1** | 找片 → 开播 → 拉对方，别来回切 App | 没解决 | 系统分享菜单递链接，2 步 |
| **R2** | 观众全屏看要清晰 | 救不了（受屏幕像素限制） | 观众本地播原片，1.0× 不放大 |
| **R3** | 看到的是"一部片"，屏幕上只允许一层控件 | 能，但要冒框错风险 | 天然成立（没有"对方的屏幕"这回事） |
| **R4** | 观众能自己拖进度，不用开口求 | 不能（第三方 App 拿不到 DOM） | 能（两边各自本地播，同步时间轴） |
| **R5** | 流量可控（手机只剩 200MB）；工作量不能是"造浏览器" | 15 MB/min 不变 | S 档近乎 0；A 档才烧流量且有上限开关 |

一句话：**取景优化的是 R3，动不了 R2 和 R4；放映厅四条都给，代价是必须处理"片源拿不到"的情况** ——
所以它得带降级档，不能只有一条路。

## 3. 方案：厅是主体，三档链路只是"怎么把画面送到对方眼里"

### 3.0 厅的生命周期（v2.1 新增，用户要求的结构改动）

```
开厅 → 对方进来（语音先通）→ 选片 → 放映 → 暂停/换片（厅不退）→ 收厅 或 转投屏
```

- **开厅不需要先有片子。** 房主点「开放映厅」→ 起隧道 → 出链接。这件事从此"一晚只做一次"。
- **对方进来看到的是"一间还没开演的厅"**，不是黑屏、不是"对方的桌面"、也不是干巴巴的"等待中"：
  房主头像 + "周周还没选片" + **语音已通（能看到对方在说话的电平）** + 反应按钮。
  这一屏是"直播间感"的真正来源 —— 比裁剪画面有用得多。
- **选片有三个入口**：别的浏览器「分享 → 双人票」递进来的链接 / 地址栏 / "最近在看"（本地记片名+进度）。
- **换片、暂停讨论都不退出厅**：链接不变，观众不用重点。
- **B 档（整屏分享）从主入口降级成厅里的一颗按钮**："给他看我的屏幕"。
  这样"教对方用手机、一起逛淘宝、打游戏"这些场景还在，只是不再绑架"看片"这条主线。

⇒ 顺带把 R1 做得比"6 步变 2 步"更彻底：**一晚上只开一次厅**，对方可以提前进来等着。

### 3.1 三档链路，按"能拿到什么"自动降级

### S 档 · 同一片源，各自本地播（首选）

房主在双人票里打开这一页 → 双人票拿到媒体地址 → **观众端直接播这个地址**，
双人票只负责递地址 + 对时间轴 + 连麦。

- 画质：观众看到的是原生 1080P/4K，不经过房主的屏幕。
- 流量：各看各的源，房主侧近乎为 0。
- 进度：两边都是真实播放器，能读能写，R4 成立。
- 回声：观众不再外放房主的屏幕声，**那条一直挂着要人耳验的 #10 在 S 档下自动不再是前提**。

**怎么拿到地址**（这是本方案的技术支点）：用 `WebViewClient.shouldInterceptRequest` 在自家 WebView 里
监听页面发出的请求，挑出 `.m3u8` / `.mp4` / `.ts` 这类媒体请求。
关键点：**即使网站的 `<video>.src` 是 `blob:`（MSE 播放），分片请求照样要经过 WebView**，
所以不需要 synctv 那种跑在服务端的站点解析器（provider）。
现有代码里已经在探测 `<video>`（`WatchSync.probeJs()`），加一路请求监听是同一层的改动。

**失败条件**：URL 绑 Cookie/Referer、签名过期、观众那边被站点拦、CORS。→ 降到 A。

### A 档 · 房主手机当中继

观众向房主手机要分片，房主手机替他取（带房主 WebView 的 Cookie/UA），再把流转发出去。
跨域/Cookie/签名一次全解，画质仍是原生。

- **架构上是延伸不是新起**：双人票本来就在手机上跑了 HTTP + 手写 WebSocket（`SignalHub`）
  并通过 Cloudflare 隧道暴露（`TunnelManager`）。要加的是一条**流式 Range 转发**（不能整包缓存，
  手机内存不允许），以及分片级限速。
- **不依赖任何第三方服务器**（用户专门问过这条）：中继进程就是手机上那个 `SignalHub`，
  对外出口就是已经在用的那条隧道。A 档不新增外部依赖 —— 唯一那条 Cloudflare 隧道今天没有它
  连邀请链接都发不出去。
- **当前裁定：先不做。** 理由不是服务器，是**该用数据决定**：等 P0 量出 S 档在真实站点上的覆盖率，
  如果掉到 B 的比例高再补 A（预计 2~3 天）。
- **代价必须摆在脸上**：观众看的量记在房主流量上，1080P 一小时约 0.6~1.5 GB。
  所以这一档默认限 720P、界面上常驻"本次已用 xx MB"，并允许房主设总量上限（到量自动降 B 或停）。
  用户余额只剩 200MB 这件事，必须在这一档的 UI 上正面处理，不能藏在设置里。

**失败条件**：EME/DRM 内容（Netflix、Disney+ 等）。→ 降到 B。

### B 档 · 屏幕像素（现状保留）+ 观众侧「只看画面」

整屏分享继续留着（逛淘宝、教操作、打游戏、DRM 影片都靠它），但把"去掉别人的 UI"这件事
**从房主侧搬到观众侧**：观众端一颗开关，默认关；打开时自动贴合内容区，留 2 像素外扩余量，
±30 像素滑杆微调，一键还原。

放在观众侧的四个理由：

1. 框错只有调的人自己知道，且**随时可逆**；房主侧框错要两个人一起难受。
2. 不触发"输出分辨率变化 → 编码器重启"的停顿。
3. 不给房主手机加逐帧处理负担（他正在放片，CPU 该留给解码）。
4. 观众想看整屏（房主去选下一集）时关一下就回去。

外加两条保险：**检测置信度低就保持整屏**（开关上标"没把握，手动开"），
**自动框一律外扩不外缩**（宁可留一圈黑边，也绝不切到画面）。

### 降级判定：不猜，探一下

观众端拿到地址后先发一个 Range 请求（看能否 200/206）+ 试解首帧。探通走 S；不通自动改 A；
A 也不行或站点是 DRM，提示房主"这一部只能共享屏幕"，一键降 B。**观众不需要自己选档**。

### 同步协议（抄来的，四家都收敛到同一套）

`(position, generatedAt, rate, version)` + 一次对钟：

- 偏差 > 1.2 s 才 seek（synctv 用 1.2s，couple-cinema 用 1.8s）；
- 小偏差用 0.94~1.06 倍速悄悄追（SyncWatch 的做法），避免画面跳；
- `version` 单调递增，用来丢弃过期指令；
- `applying` 计数器 + 衰减窗口做**回声抑制**（couple-cinema 用 700 ms，synctv 用 `_isSyncing` 800 ms + `clientOperationId`）；
- 控制消息**同时回给两端**（star-syncplayer 的思路），于是漂移是 `|t1−t2|` 而不是 `t1+t2`。

一条消息几十字节，跟流量无关。

> 顺带记下一个**现有缺陷**（与选哪档无关，都该补）：`WatchTogetherScreen.kt:144` 只有 250 ms 防抖，
> `CallSession.kt:351` 的 `wcmd` 分支裸处理，没有 `version`、没有回声抑制、没有阈值 seek。
> 观众连点 +10 时房主侧会把自己的状态回灌再触发一次。这是四家都已经踩过并修过的坑。

## 4. "要不要改造 / 自研一个浏览器"—— 正面回答

**不要。** 不是因为做不出来，是因为**它换不到你缺的那样东西**。

一起看片真正需要的是三件事：拿到片源地址、拿到播放进度、能把进度写回去。
这三件事在**我们自己的 WebView 里已经全能做**：注入 JS 读写 `<video>`（已在跑）、
`shouldInterceptRequest` 抓媒体请求（新增，量很小）。
fork 一个 Chromium 换来的主要是 DRM 和站点兼容性 —— 而 **DRM 内容本来就不能转发给观众**
（密钥绑设备，法律上也不行），所以那份增量能力对"一起看"是零。

| 路线 | 真实成本 | 多拿到什么 | 判断 |
| --- | --- | --- | --- |
| 自研 WebView 壳（多标签/书签/UA/下载） | 3~6 周，包体不变（用系统 WebView） | 与现状能力**相同**，只是更像浏览器 | 除非要当浏览器用，不值 |
| fork Chromium（Vanadium/Bromite 那种） | 半年起；跟版本；包体 +100~150 MB；自己签名；Android 16 进程模型变动要自己扛 | DRM、站点兼容、扩展 | **不建议**。一个人做是自杀式工作量，做完发现要的已经有了 |
| **递链接 + 放映厅** | **3~5 天** | 直接解决 R1~R4 | 推荐 |

**R1 具体怎么解**（不改用户习惯的那条）：

- 双人票注册 `ACTION_SEND / text/plain` 的 intent-filter → 房主在**任何**浏览器点「分享 → 双人票」，
  链接直接落到放映厅，自动填地址、自动开播、自动把观众拉进来；
- 补一颗常驻通知（"继续上次那部片 / 叫对方进来"）+ 一个桌面小组件；
- 找片仍然用他习惯的那个浏览器 —— 只是"要一起看"的那一下多按一次分享。

**内置播放器长成什么样**：建议只长成"够放片"（地址栏 + 前进后退 + 最近打开 + 播放页自动接管），
不要长成正经浏览器。浏览器是无底洞（下载、扩展、书签同步、隐私模式…），而放映厅只需要
"能把这一页打开并注入"。**越像浏览器，越做不完。**

## 5. 三家 PC 端项目映射到我们这边

| 他们的做法 | 为什么在 PC 上行得通 | 双人票的等价物 |
| --- | --- | --- |
| SyncWatch：`getDisplayMedia({preferCurrentTab, selfBrowserSurface:'exclude', systemAudio:'include'})` 选单个标签页 | 桌面浏览器能只交一个标签页，天然没有别人的桌面 | **S 档**是它的移动端等价：不交"屏幕"，交"这一页的内容" |
| synctv-app：服务端按站点解析真实播放地址，观众本地播 | 他们有 Rust 服务端跑 provider 代理、manifest 重写 | 同样观众本地播，但解析换成**自家 WebView 抓请求**；抓不到时由**房主手机**中继（A 档） |
| couple-cinema：只同步 `{paused,time,rate}`，两边各自播同一 URL | 最轻，几十字节 | S 档的传输形态就是它，补上它没有的对钟 / `version` / 阈值 seek |
| star-syncplayer：控制消息由服务器同时回给两端 | 漂移变成 `|t1−t2|` | 信令本来就在房主手机上，照抄 |
| 三家共同前提：**内容都在自己的播放器里** | 所以他们不需要处理"对方在用别的 App" | 这正是双人票的难点 ⇒ 必须有 B 档兜底 + 递链接入口 |

一个反向参照：SyncWatch 代码里明确写着"Cloudflare 没有 Android 版 cloudflared"
（`MobileServerService.java:98-101`），所以它手机当房主只能局域网/热点，Android 屏幕分享退化成
**JPEG 8~12fps 且无声**。我们的手机自跑隧道 + 真 WebRTC 屏幕流（带声音）正是它做不到的那块 ——
这三家没有一个覆盖"异地 + 手机房主"，所以不能照抄，只能抄协议层。

## 6. 实施顺序与验收判据

**P0 · 半天，先证伪两条外部事实**（不过就别开工）

1. 在自家 WebView 里挂 `shouldInterceptRequest`，打开一个真实播放页，看能不能拿到可复用的媒体地址
   （含 MSE 站点）。判据：拿到 URL 后，**用 PC 浏览器直接打开它能出画面**。
2. 探测内置 WebView 的 EME 能力。**这条我现在不下结论**：MDN/BCD 的兼容表写 WebView Android 自 v43 支持
   `requestMediaKeySystemAccess`，但我的印象是 WebView 不放 DRM 内容 —— 两者冲突，必须实测。
   它只决定"DRM 站点归不归 S/A 管"，不影响架构选择。

**P1 · 4~6 天 · 厅骨架 + S 档放映**：开厅/进厅/等候屏（含语音先通）→ 分享入口 `ACTION_SEND` →
媒体请求抓取 → 观众端本地播（hls.js 打进 `assets/viewer/`，观众页面本来就是手机自己发的，可以离线带）
+ 时间轴同步（含上面那五个数字）+ 换片不退厅。
验收：观众端 `video.videoWidth` 等于源分辨率（R2）；两端偏差中位数 < 0.3 s；连点 +10 二十次后
两端 `|Δ|` < 1 s 且不出现来回跳（R4 + 回声抑制）；从"开厅"到"对方在厅里"≤ 2 次点击。

**P2 · 2~3 天 · A 档中继**：流式 Range 转发 + 限速 + 清晰度上限 + 实时用量条。
验收：`dumpsys netstats` 量房主侧字节数，720P 一小时实测值写进 UI 文案，不靠估算。

**P3 · 1~2 天 · B 档观众侧「只看画面」**：内容区检测 + 外扩 2px + ±30px 微调 + 还原 + 低置信度不动。
验收：同一部片子 5 种内容（正常/夜景/纯黑开场/带硬字幕条/直播台标），检测框要么正确要么整屏不动，
**不允许出现切到画面**；观众端截图里 UI 像素占比降到 0。

**P4 · 1~2 天 · 房主侧流程**：常驻通知、桌面小组件、递链接后自动回到播放页。
验收：从"浏览器里找到片"到"对方进来"，点击数从 6 降到 2（脚本数 `input tap` 次数）。

## 6.9 S 档端到端实测（结论先行，细节见 §7）

链路：`drive_m0.py` 起分享拿到邀请 → 浏览器打开 → 房主进放映厅 → 嗅到片源 → 按「开始放映」。

| 观测点 | 实测值 | 说明 |
| --- | --- | --- |
| 观众端拿到的是不是原生片 | 控制台 `CINEMA_LOCAL 1920x1080 634.567`，角标「本地播放 · 1920×1080」 | **R2 达成**：屏幕流那条路最多给到 810 宽 |
| 两边时间轴 | 播放条显示 `Δ109ms`、`Δ138ms` | 在 120ms 死区里，不 seek 也不追帧 |
| 观众能不能控制 | 房主日志 `对方在控制放映：跳到 1:46`（96329+10000 换算正确） | **R4 达成**，且步进→绝对位置是房主裁的 |
| 状态回灌 | 房主每 2 秒重发一次，观众中途加入也能立刻跟上 | 后来者不用等特殊事件 |
| 收厅 | `f` 为空串时观众端撤掉本地层、退回屏幕流 | 不留黑屏 |

✅ 那条"按钮点不动"已经结清，**是量具不是产品**：同一个按钮 `document.getElementById('cFwd').click()`
一按，房主就打出 `对方在控制放映：跳到 2:06`；而浏览器连接器发的真实指针点击在
`visibilityState=hidden` 的标签页上落不进去（遮挡、权限、连接、事件绑定四项都逐一排掉：
`elementFromPoint` 命中的就是按钮本身、`onclick` 已绑定、`ws.readyState=1`、`allow=true`）。
所以按钮逻辑没问题，只是**隐藏标签页不能用来验输入**。
另外补了两个真实缺陷：没出首帧前不再显示假进度和几千毫秒的 Δ（改成"正在接上这条片源…/同步中"），
以及加了一条 8 秒看门狗 —— CDN 静默限速、签名过期这类**不报错也不出画**的情况，
原来会一直黑着，现在自动退回屏幕流并说明原因。

⚠ 还有一个**已知缺口**：S 档目前只在网页观众端生效。App 内观众端（`ViewerSession`）
没认 `cinema` 这条消息，所以在第二台手机上看还是整屏。要么补一条本地播放层，
要么在 App 内明确显示"这条片源只能在浏览器里本地播"。

## 6.96 晚进厅与 S 档收口（2026-09-25 第二轮实测）

**新增 debug 广播**：`DEBUG_SCREEN` / `DEBUG_UNSCREEN`（`am broadcast -n …/.DebugReceiver`），
把"在模拟器里点中那一行"从验证链路里彻底摘掉。不是为测试造假路径 —— 它调的就是
`CallSession.setCinemaTrack` 这个真实入口。原因：uiautomator 连着三次给出假阳性 ——
软键盘盖住候选行（点到了键盘）、地址栏里的 URL 和候选行文字相似（点错节点）、
页面加载耗时让固定 sleep 报"成功"而其实根本没递片。

**这一轮实测抓到并修掉的四个真问题**

1. **hls.js 从来没被加载**。库打进 assets、`SignalHub` 也加了 `/hls.min.js` 路由，
   但页面里**没有那个 `<script>` 标签** —— `window.Hls` 一直是 undefined。
   Chrome 有原生 HLS，照样播得出 1920×1080，于是"看起来是好的"；换 Firefox 才会当场放不出来。
   补上标签后实测 `usingHls: true`。
   （顺带排除一条误判：一开始浏览器一直拿旧页面，以为手机没发 `no-store` —— 查了
   `writeHttp` 其实早就带 `Cache-Control: no-store`，缓存是**我本地那个 python http.server** 的锅。）
2. **晚进厅的观众拿不到当前放映状态**。原来只靠放映厅那一屏每 2 秒重发，而那条循环的前提是
   **探测得到房主的页面**；房主直接打开 `.m3u8` 时 DOM 里没有 `<video>`，探针返回空 → 不重发 →
   观众永远停在"对方还没选片"，房主那边却写着"正在放映"。改成观众一连上就主动推 current
   （synctv 也是这个做法）。实测：房主先递片、观众后进厅 → 立刻拿到，标题「收口复测」、
   角标「本地播放 · 1920×1080」、`Δ118ms`。
3. **等候卡会盖在已经跑起来的播放器上**。仅语音的厅里 `gotVideo` 永远是 false，
   2.5 秒的定时器比状态推送晚到 → 进度都在走了，屏幕上还压着"对方还没选片"。
   改成"已经在放就不再弹"，并在放映到达时撤掉那个定时器。
4. **S 档下底岛那两格（屏幕流分辨率/码率、fps）恒为"—"**，挂着像画面坏了 —— 放映时收掉，
   延迟那格留着（它量的是连麦那条路，仍然有用）。

**换片**：观众端逻辑用演示钩子确定性地验过 —— 递第二条不同 URL 后
标题变、角标从 1920×1080 变成新源自己的 480×270、总时长从 10:34 变 2:00、只有一层播放条；
控制回环复测：观众按 +10 → 房主 `对方在控制放映：跳到 0:57`。

## 6.97 S 档命中率的第一版数字（2026-09-25，两轮 × 6 站）

**先把"命中"定义清楚**：不是"嗅到了地址"，是**观众那边真的出了首帧**。
所以这一轮先补了一条回执协议，再谈数字 —— 没有它，命中率就只能拿房主界面的
"正在放映"来数，而那句在对方一片黑的时候照样写着。

```
观众 → 房主：{"t":"cineack","f":"<版本>|ok|fail|<机器码>|<给人看的那句>"}
机器码：ok / badurl / unsupported / fetch / stream / start / timeout / appviewer
```

房主卡片"正在放映"后面那句副标题，现在**只由这条回执决定**，五种状态各有各的说法：
没人 · 在等 · 已播起来（附对方真的播到的分辨率）· 对方在 App 里 · 放不出（附原因）。
12 秒等不到回执就写"没等到对方的回执 · 可收厅改共享屏幕"。

**数据**（`scripts/drive_cinema_coverage.py`：每站走真实 `ACTION_SEND` → 轮询嗅探 →
`DEBUG_SCREEN_BEST` 递出**App 自己选的那条** → 读观众回执；观众是无头 Edge）

| 站点 | 第一轮 | 第二轮 |
| --- | --- | --- |
| mux 测试流 | 播出 1920×1080 | 播出 1920×1080 |
| Apple bipbop | 播出 768×432 | **放不出** `stream manifestLoadError(0)` |
| Unified 钢之泪 | 播出 224×100 | 播出 224×100 |
| Akamai sintel | **放不出** `stream manifestLoadError(403)` | 同左 |
| B 站《大航海》 | 播出 640×360 | 播出 640×360 |
| 有剧场首页 | 没嗅到 | 没嗅到 |

漏斗：嗅到可播地址 5/6（83%）→ 对方真播出来 3~4/5（50~80%）。
连跑五轮后按站点记（比"几轮平均"更有分辨力，因为抖动就在个别站点上）：
mux 5/5、Unified 5/5、B 站 5/5、Apple **3/5**、Akamai **0/5**。
⇒ 抖动全部集中在 Apple 那一条，其余四条每一轮都稳定 —— 这不是"命中率 60%"这种
一个数字能表达的事，报平均数会把"三条稳定能播 + 一条看运气 + 一条永远不行"抹平。

**能下的结论**

1. 嗅探这一层够用（含 B 站）。真正的分水岭在"对方浏览器能不能读到那条 CDN"。
2. 两轮的差值全在 Apple 那条流上，查下来是 **CDN 的 CORS 不一致**：`curl` 带 `Origin`
   打同一个 URL，有的边缘节点回 `Access-Control-Allow-Origin: *`、有的不回
   （实测两种都出现过，不回的那次 `X-Cache: HIT`）。hls.js 用 XHR 读，没这个头
   浏览器就不给读 → 状态码 0。**S 档的天花板不在我们代码里。**
3. 稳定失败那类是 403（Akamai 两轮一致）：地址过期 / 防盗链。
4. 403 与 CORS(0) 这两类**恰好都是"房主手机当中继"能救的**（同源取流、还能补 Referer/UA）
   ⇒ A 档从"看情况"变成有数可依。但当前样本里只有 1 个是国内真实站点（B 站，两轮全成），
   且"有剧场"那条用的是**首页**（首页没播放器，"没嗅到"是必然）——
   **样本不足以支撑开工 A 档**，本轮不做；下一轮拿 10+ 个真实**播放页** URL 重测，
   失败率仍 > 1/3 就做。
5. "播出"≠"好看"：Unified 两轮都只有 224×100（hls.js 起播从最低档往上爬）
   ⇒ 卡片上不再写"原生画质"这种形容词，只写对方真的播到了多少像素。

**这一轮顺带抓到并修掉的六个真缺陷**

1. `hits` 只在页面探针成功时才刷新。房主直接打开 `.m3u8` 时 DOM 里没有 `<video>`，
   探针返回空 → 屏幕写着"厅里还没选片"，日志里却明明嗅到了。改成嗅到新候选就刷
   （`shouldInterceptRequest` 在 WebView 工作线程上，必须 post 回主线程）。
   **命中率脚本第一轮整轮报"没递出"就是它** —— 那时最容易被误判成"站点都不给播"。
2. 同一条链接再分享一次**完全没反应**。第二次分享几乎总是因为第一次没成，
   现在重新加载这一页并说明在动。
3. 邀请链接原来只挂在 `State.WaitingViewer` 上：观众一进厅状态就变，房主**再也复制不到邀请**，
   `backToWaiting()` 也因此退回 Idle。改成会话里单独存一份（`CallSession.inviteUrl`）。
4. 卡片"左缘玻璃压字"定位到了：`radiusIsland` 是 **9999dp 胶囊**，圆角被钳到短边一半，
   两端变成半圆把第一行标题吃进去。多行卡改用 `radiusCard`（放映厅卡 + 同看卡），
   压在 SurfaceView 上的折射一并关掉（玻璃抓不到视频，只会把一圈黑扭着糊到字上）。
5. 回执那句长话拼在标题行里会换行、第二行压在"正在放映"上（截图实测）。
   拆成 `head`（单测按显示宽度钉死 ≤30 格）+ `detail`（另起一行）。
6. App 内观众的回执不再谎报"看的是屏幕分享" —— 有没有画面只有它自己知道；
   房主卡片照抄它报的那句。App 观众在"厅先开"的房间里，中间那块黑现在写着下一步该干什么。

**量具**（都进仓库了，别再造第二份）

- `scripts/open_room.py`：开厅 + 探活 + 落 `.dev/invite.txt`。两个坑：

## 6.98 观众是**手机浏览器**：静音自动播 + 一次点击开声音（2026-09-25）

前面所有观众端读数都是在 PC 上的 Edge 里量的。这一轮把邀请链接拿到**模拟器的手机 Chrome**
里打开，立刻暴露两件在桌面浏览器上看不见的事：

1. **一进厅就弹话筒框。** 网页端每次收到 offer 就 `getUserMedia`，而这一版麦克风本来就是
   默认关的 —— 等于对着一个随机 `trycloudflare` 域名白要一次权限。改成**点了才申请**，
   拿到轨后由观众发起 `offer` 重协商（房主的 `"offer"` 分支早就为 App 端写好了）。
   实测房主侧：`观众要加麦克风 → 收到对方音频轨 → 已发送 answer`。
2. **第一条片源必然"放不出"，其实是浏览器不肯自己出声。** Android Chrome 的自动播放政策：
   没有用户手势就不许**有声**播放。于是 `lv.play()` 被拒 → 画面出不来 → 8 秒看门狗判
   `timeout` → 退回屏幕流，房主那边还收到一条红色 fail。这不是站点问题、不是网络问题，
   是**我们把"要点一下"误诊成"放不出"**。
   改法：**先静音把画面放出来**（静音自动播放是被允许的），徽章上写"点一下开声音"，
   页面任意一处点击就把声音接上。改完实测：第一条片源直接 `ok 1280×720`，
   点击后徽章变成"本地播放 · 1280×736"、提示消失。
   顺带补一类回执 `gesture`（房主卡片写"对方点一下就开始播"，中性色）——
   万一某个内核连静音都拦，也不会再被报成故障。

**还修掉一条读代码发现的**：岛上那颗音量按钮原来只动屏幕流那个 `<video>`，
放映厅里在放的是 `lv` ⇒ "本地播放中点音量"图标翻了、声音一点没变。现在按当前在放的那个走。

**再补一条同源的误诊**：`play()` 被拒不一定是"浏览器要用户手势"。地址过期、格式不认识、
CDN 直接断开都会让 `play()` 带着别的名字失败 —— 一律报成 gesture，房主就会去等一次
永远等不来的点击。现在只认 `NotAllowedError`，其余交给 `error` 事件与 8 秒看门狗说真话。
（实测：改之前 B 站那条签名 mp4 过期被报成"点一下开始放"，改之后同一轮直接 `ok 640×360`。）

**样本扩到 11 站之后的账（§6.97 那张表 + 第二轮 5 站）**

| 结果 | 站点 |
| --- | --- |
| 稳定播出 | mux 测试流、Unified 钢之泪、B 站《大航海》《生命奇观2》《冷兵器合集》（都是 640×360 免费档） |
| 抖动 | Apple bipbop：五轮里三轮播出、两轮 CORS 读不到 |
| 递出去但放不出 | Akamai sintel：五轮全 403 |
| 根本没嗅到 | 有剧场首页、archive.org 详情页、Vimeo 一条、B 站一条 |

⇒ **"递出去了但对方放不出" = 2/8（约 25%），低于 1/3 的开工阈值 ⇒ A 档继续不做**。
⇒ 但"没嗅到"这一类里有一条是**可修的**：那四站里有两站（Vimeo、B 站那条）是
**页面还没按下播放** —— 这类站点是点了播放才去取流，没请求就没得嗅。
原来卡片只写"先让片子播起来"，现在把因果写全（不写清的那一步，房主会以为这条片子不能一起看）。

**观众环境随握手一起报上来（`VIEWER_ENV`）**：`hls=?/fail=?/mse=?/native=?/ua=?`。
起因是手机上连着几次 `timeout`，而房主那边只有一句"这条流一直没出画面" —— 分不清是
hls.js 没到位、内核不支持 MSE，还是网络根本没把清单取回来。有了这一行 + 失败回执里
的现场读数（`rs0/ns2/hls1/src1` = readyState / networkState / hls 实例 / 有没有 src），
一次运行就能定性：**这一轮是 mux.dev 本身在抽风**（同一时刻桌面 Edge 的对照站也 timeout，
而 Apple/Unified/B 站三条照常播出），不是手机、也不是代码。
顺带把原生 HLS 那条兜底路的门槛从"canPlayType 非空"收紧成 `=== 'probably'`：
手机 Chrome 对 mpegurl 回的是 `maybe`，把 src 交上去平台播放器根本不接（`ns3` 无源），
最后又是一句含糊的"没出画面"。

⚠ 一条量具教训：`cineDiag()` 最早写在 ack 那一行，而 `stopLocalPlayer()` 已经把
`cineHls` 置空、src 也撤了 —— 报出来的 `hls0/src0` 是**我自己拆出来的现场**。
读数必须在拆之前取。（这是"量具坏得像个结论"清单里的又一条。）

**看门狗改成"看进展"而不是"看秒数"**：只要 hls.js 还在推进（MANIFEST_PARSED /
LEVEL_LOADED / FRAG_LOADED 任一到达）就把截止时间往后推 6 秒。固定 8 秒会把

反复 `am start VIEW` 让 Chrome 攒到 11 个标签页，被后台限流的那个标签页才是观众，
它的 hls.js 自然不推进 —— 不是产品坏了。（判据：截图右上角那个标签计数。）

**方法论**：这几条都不是想出来的，是**把同一个页面拿到另一类设备上打开**、
以及**把样本从 6 站扩到 11 站**看到的。
以后观众端的任何结论，至少要有一次手机浏览器的实测背书。

## 6.100 「厅先开 → 人进来 → 房主再开画面」原来是一条死路（2026-09-26）

v2.1 的主体结构就是"先开放映厅、对方先进来、房主再决定给他看什么"。
把这句话真的走一遍（两台模拟器，观众已在厅里、房主之后才按分享），
一次撞出**四个**只有这条路径才有的缺陷 —— 它们各自单独看都"合理"，串起来是死路：

1. **授权被丢掉**：`CallSession.startHost` 开头那句 `if (isActive) return`
   把**刚拿到的投屏授权**也一起扔了（日志"已有进行中的分享，忽略本次请求"）。
   ⇒ 新增 `attachScreenCapture`：采到轨后 `addTrack(只加视频)` + 再发一次 offer。
2. **崩在主线程**：`addLocalTracks(vt, audioTrack)` 把**已经在同一条 pc 上的音频轨**
   又交了一遍 → libwebrtc 抛 `IllegalStateException: C++ addTrack failed`，App 直接没了。
   ⇒ 只加视频轨，并包 `runCatching`：这条路径失败不该带走整通电话。
3. **房主界面永远转圈**：`"answer"` 分支无条件 `_state = Connecting`（那是给第一次握手写的），
   而重新协商时传输一直是通的、libwebrtc **不会再报一次 CONNECTED** ⇒ 房主停在
   "正在建立直连"，观众那边画面早就到了（实测均值 39.4）。同一个毛病还有 ICE 的
   `CHECKING` 分支。⇒ 两处都改成"曾经连上过就不再退回转圈"（`iceWasConnected`）。
4. **界面在说谎**：房主一回到会话屏就写"正在分享你的手机 / 对方看到的就是你现在这一屏"，
   而厅先开根本没弹过投屏授权。⇒ 顶栏、卡片、停止按钮三处措辞全部跟着
   `CallSession.localVideo` 走：没投屏时是「语音连麦中 / 厅里现在只有语音 / 结束连麦」，
   并给出那颗缺失的**「让他看我的屏幕」**（设计里早就有，代码里一直没实现）。
   等邀请那一屏（`InviteScreen`）底部那颗按钮同理。

**观众侧还有一处同源的**（网页端，`assets/viewer/index.html`）：`startPeer` 每次收到 offer
都 `new RTCPeerConnection` ⇒ 房主中途开画面时，浏览器把正在跑的连麦整条丢掉、旧 pc 还挂着不关。
改成"有活着的 pc 就复用"（新增 `renegotiate()`：setRemote → createAnswer → 回发）。
**这一条也端到端验过了**（`scripts/drive_web_renegotiate.py`，无头 Edge + 页面自己
POST 回来的统计）：进厅时 `pcSeq=1 / vW=0`（厅里确实只有语音），房主按「让他看我的屏幕」
并过完系统弹窗之后，同一份统计变成 **`vW=540x1200`、`conn=connected`、`pcSeq` 仍是 1**
⇒ 画面接上来了，而且**没有新建第二条连接**（`pcSeq` 就是为这一句加的计数器：
一旦 >1 就是老毛病复发，连麦会被那次重建丢掉）。

**同一轮里最隐蔽的一条：画面到了，屏幕上还写着"等待对方画面…"**

`b-cinema-land.png`（横屏观众端）上房主那一屏明明已经铺在中间，正中却挂着等待文案。
是两个各自正确的写法叠出来的：

1. `var firstFrame by remember(remoteTrack) { mutableStateOf(false) }` —— 轨道从 null 变成真轨的
   那一刻，这个 state 被**重建**成 false；
2. `AndroidView(factory = …)` 只跑一次，注册给 libwebrtc 的 `RendererEvents` 一直握着
   **第一次组合时的 lambda** ⇒ 首帧回调写进了那份已经没人读的旧 state。

于是"首帧到了"这件事（日志里 `first frame rendered` 确实在）永远传不到界面。
⇒ 回调改走 `rememberUpdatedState`（永远写当前那份 state），并且 `firstFrame` 不再以
`remoteTrack` 为 key，只在轨**消失**时显式归零。
⚠ 这类 bug 只在"中途加轨"这条新路径上才露头 —— 老路径里轨从第一次组合就存在，
`remember(remoteTrack)` 再也不会变，所以一直没人发现。修完复测：观众节点树里已经没有
等待文案那一个节点（改之前它是那一屏**唯一**的节点），截图均值 48.3。

**收厅那一下：条消失了，但屏幕上没有解释（已补）**

像素对照：`.dev/tx-a-1.png`（正在放映，条在）→ `.dev/tx-b-1.png`（收厅之后，条没了、
画面还在、顶栏与控制岛都在）—— 状态本身是诚实的，**问题是观众只看到"我刚有的进度条凭空消失"**，
很容易读成"我被踢了 / 网断了"。⇒ 放映从有到无时浮一句「他停了放映，现在看的是他的屏幕」，
4.5 秒自己收起（`.dev/gone-note.png` / `.dev/gone-note-after.png` 两张为证）。
只在**曾经有过**放映状态时提醒 —— 进厅就没片的人不该看到这句话。

**回归**：两条脚本各管一条观众路径，前置都是 `scripts/open_room.py`。
- App 内观众：`check_share_after_join.py`（再配 `drive_app_viewer.py --keep-sharing`），
  四条判据 —— 房主日志「画面已接上」/ 观众 `first frame` / 观众截图均值 > 20 /
  房主顶栏翻成「正在分享」。本轮实测 `PASS`（均值 36.0）。
- 网页观众：`drive_web_renegotiate.py`，判据是页面统计里的 `vW>0` 且 `pcSeq==1` 且没有 `failed`。
  本轮实测 `PASS`（540x1200）。
63 条单测 0 失败。

## 6.101 声音档、横屏分栏、以及"回声消除到底开没开"（2026-09-26 第三轮）

用户这轮提了四件事，其中两件在动手前必须先量清楚，否则做出来的是假功能。

**1）声音三档，默认只有视频声**（`VoiceMode`）

| 档 | 画面 | 房主麦克风 | 房主听不听得到观众 |
|---|---|---|---|
| 只有视频声（默认） | 传 | **对方本地播原声时自动关**；屏幕分享时开着 | 不听（下行静音） |
| 视频声 + 连麦 | 传 | 一直开 | 听 |
| 只连麦 | 不传 | 开 | 听 |

必须先说清的一条事实：**"把手机里正在放的声音原样传过去"这套 SDK 做不到**。
本机 AAR 的 `JavaAudioDeviceModule` 只有读样本的回调（`setSamplesReadyCallback` /
`setAudioBufferCallback` / `setPlaybackSamplesReadyCallback`），**没有往采集里写样本的入口**
（javap 过，没有 `createAudioRecordInputChannel` 之类），`AudioSource` 也没有自定义处理器。
所以"手机声"在整屏分享时只能靠外放灌麦克风 —— 那一档**绝对不能关麦**，关了观众就是全哑。
反过来在放映厅里观众拿的是原生音轨，房主再传一遍外放就是迟到半拍的第二份声音，
那正是用户听到的"回声"，所以收到 ok 回执之后要自动关。两条判断都做成纯函数
（`hostMicNeeded` / `hostHearsViewer`）钉在 `VoiceModeTest` 里。

房主侧"听不到观众"用的是 `setSpeakerMute`：它只清零 libwebrtc 自己那条下行 AudioTrack，
房主外放的影片声不受影响。中途改档不需要重新协商，所以 m-line 保持 sendrecv。

**2）回声消除：以前那句"默认就会启用 AEC/NS/AGC"是猜的，测完发现默认是"谁都不开"**

三条实测出处（都在 `io.github.webrtc-sdk:android:150.7871.01` 里）：

· 约束键名：`libjingle_peerconnection_so.so` 里能找到的音频处理约束只有
  `echoCancellationMode` / `noiseSuppressionMode` / `autoGainControlMode`
  （取值串 `unspecified` / `disabled` / `platform` / `software`）和老的 `goog*` 一族；
  **裸的 `echoCancellation` 不在**（它是 `echoCancellationMode` 的前缀，链接器只合并公共
  后缀，真被引用就一定会单独出现）。所以写 `echoCancellation=true` 这种"网上都这么写"
  的键，在这版上是一个字都不生效。
· `WebRtcAudioRecord.shouldUsePlatformEffect(...)` 反编译出来是
  `requested && isSupported && mode != SOFTWARE` ⇒ 只有**明确点名 software** 才让软件 AEC 上位。
  空约束 = `unspecified` ⇒ 设备没有硬件 AEC 时（模拟器、一部分机型）**两条路都没开**。
  真机报 `hwAec=true`、模拟器报 `false`，正好是这条分界线。
· 同一份 .so 里的校验语句：`Platform echo cancellation cannot be combined with software
  noise suppression`、`Software fallback is disabled by platform mode.`
  ⇒ AEC 与 NS 必须同一档；一旦要了 platform 而设备起不来，软件兜底是被关掉的。

于是规则改成**按设备二选一**（`RtcEngine.audioSourceConstraints()`）：有硬件 AEC 就交给它
（不加约束，保持 unspecified + ADM 的硬件请求），没有就显式要 `software` 的 AEC3 + NS。
AGC 一律不点名 —— 房主外放里是影片声，自动增益会把整段影片按"说话"来泵音量。
"支持了"这三个字用 `getPlatformAudioProcessingState()` 打进 logcat 自证：

```
RtcEngine: libwebrtc initialized; hwAec=false hwNs=false
RtcEngine: 音频源约束：无硬件 AEC → 显式启用软件 AEC3 + NS
RtcEngine: 平台音频处理[host] INDEPENDENT AEC{available=false requested=false active=null} ...
CallSession: 声音档[建轨] VideoOnly 对方本地播=false 手动静音=false 覆盖=false → 麦克风=true 房主听对方=false
```

用户明确说"只需要支持，暂时不用测试"，所以**耳朵那关仍然没验**（任务 #10 留着）。

**3）"App 一打开就是横屏"有两条来路，都堵上了**

· 观众侧那颗「方向：跟随/竖屏/横屏」的选择被写进 SharedPreferences，跨会话、跨重启都活着；
  而 `ViewerSession` 是进程级单例，那场观看没散之前回到首页、甚至重开 App 都停在横屏，
  偏偏**能改它的按钮只在观看界面里**。实测证据：`t2view` 的 `t2.xml` 里躺着
  `viewer_orientation=Landscape`（我自己截图时点的）。改成只管这一场，散场回"跟随"，
  启动时顺手把这个已经没人读的键清掉。
· 交还方向不能只写 `SCREEN_ORIENTATION_UNSPECIFIED`：关掉自动旋转的手机上系统不再问传感器，
  用的是"最后一次生效的方向"，于是为看横屏片做的那一转会一直留着。现在显式要回
  `Settings.System.user_rotation` 那一档（自动旋转开着时才用 UNSPECIFIED）。

**4）横屏放映厅改成左右分栏**

2400×1080 上纵向只有约 390dp，竖屏那套"顶栏 + 地址行 + 胶囊行 + 底部卡"摞下来，
留给画面的权重只剩一两百 dp —— 一块横屏手机放不了一个横屏视频，本末倒置。
现在画面在左（吃掉屏宽减去 320dp），地址/动作/状态卡在右栏。
状态卡用 `weight(1f, fill = false)`：给满权重实测是一块下面全空的黑玻璃，
完全不给又会在展开嗅探时把最后一行顶出屏幕外没得滚。
三颗测试胶囊（换一条流/本地测试页/HLS 测试流）搬进「展开嗅探」—— 它们是量具，
不该和「开始放映」抢同一行；依赖它们的 `drive_cinema_*.py` 改成先点面板。

**5）这一轮真抓到的一个缺陷：「分享 → 双人票」只开屏、不开厅**

`CinemaScreen` 的注释写着"非空就直接开厅放这一页"，代码里却只置了 `showCinema = true`：
没有信令、没有邀请链接、卡片上"复制邀请"那一行根本不出现，而顶栏还写着"厅已开 · 等对方进来"。
实测 `.dev/title-01-host.png`：从分享入口进来嗅到了 2 条可播地址，可观众那边连门都没有。
改成走 `openCinema()`（`enterCinema`），并且先进这一屏再要权限，别把用户递进来的链接吞掉。

顺带一条同源的：`LaunchedEffect(initialUrl)` 只以 URL 为 key，**同一条链接第二次递进来
什么都不会发生** —— 而人重复分享，多半正是因为第一次没成。加了 `cinemaSeq` 一起当 key，
`handledShare == u -> 重新加载这一页` 那句原本就写好的分支这才第一次真的跑到。

**6）量具这一轮坏了三次，其中一次让我"修"了一个不存在的缺陷**

· `check_cinema_title.py` 第一版取 CDP 的第一个 page target，而 Edge 会插一个
  `edge://sync-confirmation-dialog/` 的同步推广页排在前面 —— 量的一直是那个弹窗，
  `ws/cine` 全空，于是我"实测"到"晚进厅的观众拿不到放映状态"，还为此加了一次广播。
  那个缺陷**不存在**：`init` 里 `viewerConnected` 一跳真就推 current（22ab325 修的就是它），
  而 `SignalHub.detach` 会把这一位落回 false，连信令重连都覆盖到。
  判据改成"认 URL 不认位置"之后，没带我那两处的代码一次就 PASS。重复广播已撤回（167b9e9）。
· `Cdp.eval` 回的是 `{"value": ...}` 而不是裸字符串，按裸字符串解会永远得到空 dict ——
  和上一条合起来把"读不到"伪装成了"产品坏了"。
· 放映厅卡片那行标题改从 logcat 取：按"含 ` · ` 且不含 http"在 uiautomator 里挑节点，
  会挑中顶栏的"厅已开 · 等对方进来"（第一版就是这么把标题读错的）。
  另外 `audit_app_layout.py` 的 SQUISHED 加了绝对下限，否则"只有视频声"这种
  故意做小（10.5sp）的辅助行会被报成被裁，而截图上它清清楚楚是一整行。

**验收**：`scripts/check_cinema_title.py` PASS —— 房主卡片与观众放映条逐字相同
（`test-streams.mux.dev · 193039199_mp4_h264`），换一条流之后两边同时变成
`test-streams.mux.dev · master`；横屏放映厅 `audit_app_layout.py` 零越界零压字
（未选片 / 放映中 / 展开嗅探三态各量一次）；71 条单测全绿。
没验的：App 内观众端那条镜像条（t2view 被另一个 agent 占着，它绑的是同一个
`cinema.track.title` 字段）、真机横屏、以及回声的人耳效果。

## 7. P0 实测结果（2026-09-25，模拟器 t2test + 真实站点）

跑法：`scripts/drive_cinema_probe.py emulator-5556 <url>` —— 用**真实分享意图**
（`am start -a SEND -t text/plain --es android.intent.extra.TEXT …`）打开放映厅，
14 秒后从 logcat 捞 `Cinema` 标签的三类读数。

| 测的东西 | 结果 | 结论 |
| --- | --- | --- |
| 请求流嗅探（HLS） | Mux 测试流：抓到 `x36xhzz.m3u8` + 一条变体 `.m3u8` | 清单类能抓到 |
| 请求流嗅探（真站点） | **B 站 `BV1GJ411x7h7`：抓到 `upos-sz-…bilivideo.com/…_da2-1-16.mp4?e=…` 一条直链** | **S 档成立**：不需要服务端 provider，自家 WebView 就能拿到观众可播的地址 |
| 页面自述 | `blob=false dur=634s size=1920x1088` / `640×360·60s·直链` | `currentSrc` 是真实 URL 的情况比预期多（Android WebView 原生放 HLS） |
| **EME / DRM** | `api=true` 但握手 `NotSupportedError: Unsupported keySystem` | **API 在、DRM 栈不在** —— MDN 那句"WebView 自 v43 支持"只说了前半句；Netflix 那类确定走不了 S/A，必须留 B 档 |
| 递链接入口 | `ACTION_SEND` 冷启动与 singleTop 二次分享都接得住 | R1 的入口成立 |

顺带抓到一个真 bug（已修 + 加测）：B 站埋点 `data.bilibili.com/log/web?…|…_da2-1-16.mp4|quit`
把片名塞在查询串里，整条 URL 匹配后缀会把它当成"单文件片源"端给房主 ——
房主一点，观众必然放不出来。改成**只在路径上看后缀** + 埋点域名黑名单。
修完同一条 B 站地址的候选数从 2 → 1，且留下的那条是真的。

**还没量到的**：MSE 站点（`currentSrc=blob:`）的覆盖率、需要登录的站点、以及
"抓到的地址观众那边直接放"的成率（B 站这类直链绑 Referer/UA/IP，很可能要 A 档才成 —— 下一步就量这个）。
`https://www.w3schools.com/html/mov_bbb.html` 那次抓到 0 条，**原因未定**（页面可能根本没加载出来，
不是嗅探失败），别当成反例。

单测：`scripts/run_unit_tests_ascii.sh` → 48 条全绿。
⚠ 为什么绕这一圈：项目在 `G:\工作台\`（中文路径）下，Gradle 测试工作进程能启动、
JUnit 能加载，但**每个测试类都 ClassNotFoundException**（连既有全绿的用例也一样），
`clean` / `--no-configuration-cache` / 换 JDK 21 都救不回来；同一份代码复制到 ASCII 路径就正常跑。
**这是量具坏了，不是代码坏了** —— 别把它读成"我的改动把测试搞崩了"。

## 8. 其余未决

- MSE 站点抓到的往往是**分片清单 + 一堆 header 要求**，S 档能覆盖的站点比例要先量一遍再承诺（P0-1 的产出）。
- A 档中继会不会被站点判定为异常流量（同一 Cookie 换 IP 取片）—— 需要实测，且这是"能救回来多少"的上限。
- 递链接进来后，如果那一页需要登录而观众没登录：走 A 档（借房主的会话）还是提示"你登录一下"，产品上还没定。
- 跨网真机复验仍然欠着（手机在忙）；S 档第一次真实跑通，最好就在真机 + 真实站点上做。

## 9. 已定的与待拍的

**已定（用户 2026-09-25 裁定，不再问）**

1. **先做 S 档**（放映厅一步到位），观众侧那颗「只看画面」留到 B 档一起做。
2. **A 档中继缓做** —— 等 P0 量出 S 档覆盖率再决定（**不是**因为要服务器：中继就在房主手机上）。
   → 2026-09-25 数出来了（§6.97）：嗅到 83%，对方真播出来 60~80%，两类失败（403 防盗链、
   CDN 不给跨域读）**都只有中继能救**。但真实站点样本太少（国内站只测了 B 站，还测了个首页），
   所以维持"不做"，触发条件改成硬的：**10+ 个真实播放页样本、失败率仍 > 1/3 就开工**。
3. **内置播放器只做"够放片"**：地址栏 + 前进后退 + 最近在看 + 播放页自动接管，**不长成正经浏览器**。
4. **厅先开、人先进来、片子后选**（v2.1 的主体结构）。

**待拍（厅先开之后新冒出来的三条）**

1. **N1 观众在厅里能"点单"吗？** 推荐：能递链接进来，但放不放由房主决定。
   （成本很小：递链接这个入口本来就要做，观众端多一个输入框 + 一条信令消息。）
2. **N2 厅在后台能活多久？** 推荐：复用 `ShareService` 那套前台服务保活，通知栏常驻一颗"回厅里"。
   ⚠ 国产 ROM 杀后台这条只能真机验，而真机现在被用户占着。
3. **N3 没选片时观众看到什么？** 推荐：等候屏 + 语音已通（能看到对方在说话的电平），
   投屏要房主主动按。备选：语音默认不开（免得突然被听到）、或直接进整屏分享。
