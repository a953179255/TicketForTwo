观众端 · 播放器化改造（提案效果图）

现状只有"顶栏 + 底部一颗控制岛"，看视频时屏幕上一直压着两块玻璃，且没有任何播放控制。 下面四态是提案：① 沉浸态（控件自动收起）→ ② 控件态（轻触唤出）→ ③ 手势态（左半屏上下滑=亮度、右半屏=音量）→ ④ 横屏铺满（旋转按钮）。 配色与圆角沿用现有玻璃规范（accent #2997FF、pill 9999、控制岛 surfaceAlpha 0.72）。

④ 横屏铺满。对方发的是竖屏（810×1800），你横过来看时按 contain 只有中间一条。 「旋转」按钮把画面转 90° 铺满整块横屏 —— 这是播放器里最常被按的一个， 也是只有 App 能做得干净的一类：网页要转得靠 CSS transform，且全屏本身在安卓各家内核上就不稳。

这些能力 App 与网页各自的边界

能力App 内观看网页观众端依据
屏幕亮度手势可以，真亮度做不到 本机 Chromium 实测 screen.setBrightness / getBrightness / mozBrightness 全部 undefined；网页只能给画面盖一层半透明黑（假亮度）
音量手势可以，走系统音量部分：video.volume 能调 volume 属性实测存在；但它调的是这个播放元素的音量，不是系统音量；iOS 上是否可写本机没有设备未验
全屏本来就是全屏各家内核不一 已实测：安卓上对 documentElement 调用会被拒；改成请求 #stage 后仍需以 fullscreenElement 复核
锁定/切换方向可以，Activity 级要先进全屏，且标 Limited availability MDN：orientation lock 通常仅移动端 + 全屏可用，否则抛 SecurityError
画面旋转 90° 铺满渲染层直接转CSS transform 能凑 网页要自己处理容器尺寸与手势命中区，容易和全屏互相打架

保持屏幕常亮FLAG_KEEP_SCREEN_ONWake Lock API 可用 navigator.wakeLock.request 实测存在
进度条拖动不适用不适用 这是直播流不是录像，没有可拖的时间轴；做出来反而是假的
倍速播放不适用不建议 playbackRate 存在，但对实时流会直接失同步、堆缓冲

结论：你的判断是对的，而且比"浏览器难统一"更具体。 亮度这一项网页根本没有 API（不是各家实现差异，是压根没有）；音量只有"元素音量"，不是系统音量； 全屏与转向是"各家内核行为不一致"。所以播放器化的手势与旋转，App 端做完整版，网页端做降级版： 网页保留轻触唤出控件 + 元素音量 + 画中画 + 常亮，亮度改成"画面变暗遮罩"并如实标注， 旋转不做（避免和各家全屏实现互相干扰）。 另外两条我刻意不做：进度条和倍速 —— 这是实时直连，不是录像，做了就是骗人。
