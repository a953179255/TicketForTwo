放映厅（v2.1）—— 厅先开，人先进来，片子后选

上一版的「取景」你否掉了，两条理由我都认；第二条尤其关键，它把我没想透的地方暴露出来了： 糊不糊，跟裁不裁没关系 —— 只要画面是从房主屏幕截下来的，上限就是那块屏幕的像素，裁一刀改不了天花板。 所以核心换成另一句话：要一起看清一部片，就别传画面，传片源。 而你补的那条（先开厅、对方先进来、我再选片）改的不是按钮位置，是主体： 厅才是入口，放映是厅里的一个动作 —— 见第 3 节。

所以这版的核心换成了另一句话

要一起看清一部片，就别传画面，传片源。观众自己把那条流播出来，画质是原生的， 屏幕上只有他自己一层控件，进度是真的能同步的 —— 你提的"割裂 / 双层 UI / 全屏糊"三条一起消失， 而且不需要任何"框"。双人票要做的从"摄像机"变成"放映机 + 对表员"。

S 档 · 同一片源各自播。房主手机只做两件事：把媒体地址递给观众、把时间轴对齐。 观众端是真的在播那部片，不是看录像 —— 原生清晰度、真进度条、能自己拖，双人票的流量近乎为零。 拿地址这步靠 WebViewClient.shouldInterceptRequest：就算网站的 <video>.src 是 blob:（MSE），分片请求也照样要过我们的 WebView。

A 档 · 房主手机当中继

观众打不开这个源时，让房主手机替他取

跨域、要 Cookie、签名 URL、观众那边被站点拦 —— 这些在 S 档会失败的情况， 都由房主手机做一层流式转发解决。不需要任何第三方服务器： 双人票本来就在手机上跑了 HTTP + WebSocket（SignalHub）并已通过隧道暴露出去， A 档只是给这个已经在你手机上的服务加一条 Range 转发。 外部依赖没有增加 —— 唯一那条 Cloudflare 隧道今天就已经在用了，没它连邀请链接都发不出去。

但这一档我建议先不做，理由不是服务器，是该用数据决定： 等 P0 量出 S 档在真实站点上的覆盖率，再决定要不要花这 2~3 天。真要做，代价是观众看的量算房主流量 （1080P 一小时约 0.6~1.5 GB），所以它必须自带清晰度上限 + 实时用量条 + 总量熔断。

B 档 · 屏幕像素（现状保留）

DRM 站点唯一的解，且把"框"搬到观众手里

Netflix/Disney+ 这类放不了 S/A。退回整屏分享，但加一颗观众自己的 「只看画面」开关：自动贴合内容区，不满意可以微调，一键还原。 见第 4 节 —— 这颗开关就是取景 v1 该变成的样子。

降级怎么判

不猜，试了才知道

观众端页面拿到地址后先探一次（发一个 Range 请求，看能不能回 200/206、 首帧能不能解码出来）。探通走 S；探不通自动改走 A（房主中继）；A 也失败或站点是 DRM， 就提示房主"这一部只能共享屏幕"，一键降到 B。整个过程观众不用选。

语音不变

连麦这一路照旧

三档里语音都是同一条 WebRTC 音频，跟画面解耦。S/A 档下观众端不再需要"屏幕声音"这条轨 （声音是他自己播出来的），回声问题自动消失 —— 那条一直挂着等验证的 #10 在 S 档下不再是前提。

同步协议（抄来的）

四个数字就够

(position, generatedAt, rate, version) + 对钟：偏差 >1.2s 才 seek， 小偏差用 0.94~1.06 倍速悄悄追（synctv / SyncWatch 都是这个套路）， version 用来丢过期指令，applying 计数器防回声。 一条消息几十字节，跟流量无关。

强迫症这条正面回应

不做"一个框"，做"贴边 + 余量"

自动检测给的是外扩 2 像素的框而不是精确框：宁可留一圈黑边， 也绝不切到画面。黑边在播放器里是正常现象，切掉演员半张脸不是。 滑杆只在 ±30 像素范围内可调，超出就吸附回检测值。

还有一条保险

检测不确信就不动

夜景片、纯黑开场、刚切 App 这几类，检测置信度低 → 保持整屏， 开关上标一句"没把握，手动开"。默认关，观众不点就永远是他熟悉的整屏。

你问的那个问题，正面回答

要不要改造 / 自研一个浏览器？

不要。不是因为做不出来，是因为它换不到你缺的那样东西。 你要的其实是三件事：拿到片源地址、拿到播放进度、能把进度写回去。 这三件事在我们自己的 WebView 里已经全能做 （shouldInterceptRequest 抓请求、注入 JS 读写 <video>， 后者已经在跑）。fork 一个 Chromium 换来的主要是 DRM 和站点兼容 —— 而 DRM 内容本来就不能转发给观众（密钥绑设备，法律上也不行）， 所以那份能力对"一起看"没有增量。

成本对比：自研 WebView 壳（多标签/书签/UA）3~6 周、包体不变； fork Chromium 半年起、跟版本、包体 +100~150MB、要自己签名； "递链接 + 放映厅"3~5 天。一个人做 fork 是自杀式工作量，而且做完发现要的功能已经有了。

但有一个真实的口子

内置播放器要不要长成"正经浏览器"

建议不要长成浏览器，只长成"够放片"：地址栏 + 前进后退 + 最近打开 + 一个"这是不是个播放页"的自动接管。理由：浏览器是个无底洞（下载、扩展、书签同步、隐私模式…）， 而放映厅需要的只是"能把这一页打开并注入"。越像浏览器，越做不完。

6那三家 PC 端项目，映射到我们这边是什么

他们（PC / Web）的做法为什么那样行得通双人票的等价物
SyncWatch：getDisplayMedia 选单个标签页 + systemAudio:'include' 桌面浏览器能只交一个标签页，天然没有别人的桌面 S 档就是它的移动端等价：不交"屏幕"，只交"这一页的内容"
synctv-app：服务端按站点解析真实播放地址，观众本地播 他们有 Rust 服务端，可以跑 provider 代理、manifest 重写 同样"观众本地播"，但解析换成自己 WebView 里抓请求；解析不到时由房主手机做中继（A 档）
couple-cinema：只同步 {paused,time,rate}，两边各自播同一 URL 最轻，一条消息几十字节S 档的传输形态就是它，但补上它没有的：对钟、version、阈值 seek
star-syncplayer：控制消息由服务器同时回给两端 漂移变成 |t1−t2| 而不是 t1+t2 信令已经在房主手机上，照抄：一条指令回给两端，别只回给发起方
三家共同点：都假设"内容在自己的播放器里" 所以他们永远不需要处理"对方在用别的 App" 这正是双人票的难点，也是为什么必须有 B 档兜底 + 递链接入口

顺带一个 SyncWatch 帮不上、而我们已经有优势的地方：它代码里明确写着 "Cloudflare 没有 Android 版 cloudflared"，所以手机当房主只能局域网/热点。我们的手机自跑隧道 + 真 WebRTC 屏幕流（带声音）正是它做不到的那一块 —— 这三家没有一个能覆盖"异地 + 手机房主"。

7你已拍的三条 + 厅先开之后新冒出来的三条

已定 · 不用再看

Q1 先做 S 档（放映厅一步到位，观众侧那颗「只看画面」留到 B 档一起做）。 Q2 A 档先不做 —— 但纠正一下理由：A 档不需要第三方服务器，中继就跑在你自己手机上 （SignalHub 已经是手机上的 HTTP 服务，隧道也已经在用）。真正"先不做"的理由是该用数据决定： 等 P0 量出 S 档在真实站点上的覆盖率，掉到 B 的比例高再补 A。 Q3 内置播放器只做"够放片"：地址栏 + 前进后退 + 最近在看 + 播放页自动接管，不长成正经浏览器。

N1 · 观众在厅里能"点单"吗？

厅先开之后多出来的问题：对方进来干等着，还是也能把自己想看的链接递进来给你挑？ 成本很小（递链接这个入口本来就要做，观众端多一个输入框 + 一条信令消息）。

能点单：他递链接进来，你决定放不放（推荐） 不能，选片权完全在房主 能点单，且房主设了"自动接受"

N2 · 厅在后台能活多久？

你切去浏览器找片这段时间，厅必须一直在 —— 现在分享是跑在 ShareService 前台服务里的， 放映厅要复用同一套保活。风险是国产 ROM 杀后台（这条只能真机验）。

前台服务常驻，通知栏一颗"回厅里"（推荐） 只保 10 分钟，超时提示重开

N3 · 没选片的时候，观众看到什么？

第 3 节那屏"周周还没选片 + 语音已通"是我推荐的形态。另一条路是这时候允许房主投屏（B 档）先聊着。

等候屏 + 语音，投屏要房主主动按（推荐） 等候屏，但语音默认不开，省得突然被听到 直接进整屏分享，选片也在里面完成

开工前我先花半天验两条外部事实（不通过就不承诺 S 档）： ① shouldInterceptRequest 在真实站点上能不能抓到可复用的媒体地址 —— 这个数出来才知道 S 档覆盖率、也才知道 A 档到底要不要做； ② 内置 WebView 到底有没有 EME（MDN 的兼容表说 WebView Android 从 v43 支持 requestMediaKeySystemAccess，但我的印象是 WebView 不放 DRM 内容 —— 这条我没实测，不下结论，它只决定 DRM 站点归不归 S/A 管）。 探针做成厅里的一个调试页，跑完就顺手变成放映厅的片源层。
