从「分享屏幕」到「一起看片」

你说的三件事我拆成一句话的方案：在房主手机上做「取景」，只把视频那一块编成画面推过去。 观众收到的就不再是"别人的手机桌面"，而是一段干净的视频流 —— 于是他的控件是屏幕上唯一一层 UI， 自然就像进了直播间 / 打开播放器；而房主那边爱用哪个浏览器用哪个浏览器，不用换成 App 内置的。

① 画面层：逐帧裁掉房主的 UI、状态栏、通知 ② 观众层：直播间化，只有一层控件 ③ 控制层：能控就控，不能控就"点歌式"请求

顺带解决的两件事

隐私是白送的

裁掉的不是像素而是数据：房主的微信弹窗、验证码、通知、地址栏里的历史记录， 观众根本收不到，不是"到了对端再涂黑"。这一条比涂黑强得多。

同样白送

码率花在片子上

原来 720p 的额度里有一大半在传房主的黑色 App 背景和状态栏文字。裁掉之后同样的码率全给画面， 片子更清楚、还更省流量。

取景框来源 · 优先级 1

自动：黑边检测

全屏播放时视频上下常带黑边。每 ~2 秒抽一帧统计亮度，找出"四周全黑、中间有内容"的最大内接矩形。 零操作、零权限，覆盖"全屏看电影"这个主场景。

优先级 2

手动：拖一次

非全屏（小窗、网页里嵌一块播放器）时黑边检测会失手，房主点「调整取景」拖一下。 按横竖屏各记一份，下次自动恢复。

优先级 3

内置浏览器：直接问 DOM

用 App 里那个「一起看片」时，<video> 的位置尺寸是精确已知的， 取景框可以零误差贴合，还能同时拿到片名和进度。

失败兜底

检测不确信就退回整屏

置信度不够（画面本来大片纯黑、或刚切 App）时不动框，宁可多传 UI 也不把片子裁掉半张脸。 顶栏标一句"未取景"。

4「让对方也能控制进度」的三条路，各自能做到什么

路线画面质量流量观众能直接控制进度权限能看什么内容
A 取景直播
推荐做底座		 重编码，720p/2Mbps 档约 15 MB/分钟 否（只能请求）无新增 任何 App：Netflix、B 站、本地播放器、网盘
B 内置浏览器
现状，保留		 同上（也可以走取景只传画面）约 15 MB/分钟 是（注入 JS，精确到秒）无新增 只有本网页播放器，别的 App 进不去
C 链接同播
synctv 那套		 观众本地原生播放，无损几乎为零（只传时间戳） 是（双方各自本地播，同步时间轴）无新增 观众那边也得打得开这个源；会员/DRM 直接废

我的建议：A 当底座（它解决的是"割裂"和"双层 UI"这两个你真正难受的点，而且对任何浏览器都成立）； B 保留成"要对方帮你拖进度时才进"的模式；C 作为 A 的升级按钮 —— 当同看的内容恰好是个能直接打开的链接时， 观众端出现一颗"用我的账号看高清"，点了就换成本地播放 + 只同步时间轴，两个人都不用心疼流量。

C 的代价要说清楚

它不是"更好的 A"，是另一件事

C 传的是片源不是画面，所以"我在看什么"必须能被对方独立复现。 情侣两人会员不在同一个账号上时，这条路当场断掉，只能回 A。 所以它是加分项，不能当主方案。

还有一条更狠的，我不建议

无障碍服务代按

开了无障碍就能读第三方 App 的控件、直接替观众点 ±10 秒。代价：房主要授予系统级权限、 Flyme/MIUI 会杀、重装会掉、误点风险，而且"对方在我手机上点按钮"这件事本身让人不安。 除非你明确要，我不做。

5你给的四家，各自解决的是哪一半

我把四个仓库都读了源码（不只是 README）。结论有点意外：没有一家做"逐帧裁剪" —— 因为它们都不需要：桌面端可以直接选"一个标签页"，Web 端可以各自本地播。 只有手机当房主 + 内容在第三方 App 里这个组合需要裁剪，而这个组合上四家全都退化了。

项目它怎么拿到画面我们能抄什么为什么不能照搬
synctv-app
Flutter，活跃，72★		 服务端按站点解析出真实播放地址（Rust 的 bilibili/client.rs），观众本地播自己的播放器 整套时间轴同步模型：(position, generatedAt, rate) + NTP 式对钟 + 偏差 >1.2s 才 seek + 单调 version 丢过期帧 + 回声抑制 要一个跑在服务端的 provider 代理（manifest 重写、签名 URL、切片缓存）。手机跑不了，也不该跑
SyncWatch
Node+Socket.IO，活跃，134★		 桌面：getDisplayMedia({preferCurrentTab, selfBrowserSurface:'exclude', systemAudio:'include'}) 选单个标签页
Android：MediaProjection→ImageReader→JPEG 8–12fps、无声		 「申请控制权」这个交互（= 我说的请求式）；共享时把自己的播放控件全禁掉；immersive 去系统栏；直播间浮层清单（状态卡 / 延迟 / 偏差 / 反应层） 它自己写了"Cloudflare 没有 Android 版 cloudflared"⇒ 手机当房主它做不到公网；我们的隧道 + 真 WebRTC 屏幕流正是它缺的那块
192_lab-couple-cinema
Node，单次提交，像课程作业		 只同步 {paused,time,rate}，双方各自播同一个 URL（hls.js） 回声抑制的具体写法：一个 applying 计数器 + 700ms 衰减，跟随者 |Δ|>1.8s 才 seek。我现在的 WatchSync 只有 250ms 防抖，缺这一条 片源是灰产 m3u8 采集站；语音只有 Google STUN 没 TURN，对称 NAT 下必挂
star-syncplayer
JavaFX+VLC，2023 年后停更		 双方各自打开本地同一个文件，谁都不传画面 服务器把控制消息同时回给两端，于是漂移是 |t1−t2| 而不是 t1+t2 —— 一条很便宜的信令改进 桌面 VLC，且要求两人有同一个文件；默认服务器 2024-09 已过期

所以方案这么定：画面层用「取景」（四家都没有、也只有我们需要）；观众层抄 synctv/SyncWatch 的直播间浮层； 控制层抄 SyncWatch 的「申请控制权」+ 那两家的漂移/回声模型；「链接同播」作为可选升级，抄 synctv 的同步协议而不是它的代理。

6要你拍的三个问题

Q1 · 取景默认开还是默认关？

开了以后观众只看到片子；但有些场景（教对方用手机、一起逛淘宝、打游戏）整屏才是对的。

自动判断：识别到全屏视频就取景，否则整屏 默认整屏，房主手动开「电影模式」 默认取景，房主手动切「看我的屏幕」

Q2 · 观众用别的浏览器时，控制做到哪一档？

真·代按要无障碍权限；请求式零权限但要房主动手。

请求式（房主手机弹提示，他自己按） 请求式 + 房主可临时授权代按 不做控制，只保留连麦喊话

Q3 · 「链接同播」（C）要不要一起做？

省流量最狠（约 15 MB/分钟 → 接近 0），画质原生；但只有双方都能打开同一个源才成立。

先做 A，C 留到下一轮 A + C 一起，观众端加"用我的账号看高清" 只做 C，画面共享保持现状
